# KAIROS｜契機

**Knowledge-building Assessment Integrating Reading comprehension and Online Scaffolds**

**線上版：https://wanghsinyun-cyber.github.io/blank-app/**

整合「閱讀理解診斷 × KIDMAP」、「Knowledge Forum 知識建構」與「評量即學習」的 AI 助評研究原型。
領域為**國小四—六年級閱讀理解**，理解歷程架構採 **PIRLS 2011 四項理解歷程 × 19 項子歷程**。

三條線接成一個迴圈：

1. **診斷 → 問題**：把 KIDMAP 第二象限（能力足以答對卻答錯）的題目一鍵轉成知識建構視圖的共同問題。
2. **評量即學習**：在作答的當下配置 AI 夥伴——導師／學生／同儕三種角色，加上系統鷹架對照組，
   四條件以班級為單位叢集隨機分派；提問功能跨角色恆定，只有社會框架不同。
3. **歷程證據**：完整事件日誌 → 延宕序列分析、認知網絡分析、情感軌跡、
   共變數分析與中介路徑，最後用「Δθ × 知識建構指數」雙軌檢核討論有沒有真的變成理解。

完整設計說明：[docs/系統設計說明.md](docs/系統設計說明.md)

## 快速開始

建置（把 `src/` 依檔名順序串成單一 HTML）：

```bash
bash build.sh
```

產物 `dist/index.html` 是單一檔案（目前 443,244 bytes）：沒有框架、沒有打包工具鏈、沒有 npm 相依。
唯一的外部資源是 Google Fonts（Noto Serif TC 600/700、IBM Plex Mono 400/500/600），
字型載不到會落回系統字型，功能不受影響。直接用瀏覽器開啟就能跑。

若要用本機伺服器預覽（Windows，不需 Node）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\serve.ps1 -Port 8765
```

## 三種身分看到的東西不一樣

| 身分 | 側欄 |
| --- | --- |
| **研究者**（super user） | 全部：教師後台、建立派題、派題分析、研究控制台、知識建構空間、雙軌評量儀表板、文本與題庫、系統設定、系統說明 |
| **教師** | 只有四項：教師後台、派題分析、知識建構中心、雙軌評量儀表板。研究控制台、建立派題與系統設定屬於研究端的操作，側欄看不到，直接打網址也會被擋下 |
| **學生** | 我的作業、知識建構空間、我的學習軌跡、前後測問卷、系統說明 |

**知識建構空間對學生是「測驗之後才開放」的**：只要還有指派給他而未交卷的作業，
四個入口（視圖列表、視圖畫布、單篇貼文、想法串綜整）都會導向一個門檻畫面，
側欄也會標示「測驗後開放」。理由是系統迴圈的次序——先作答才有診斷，
才有值得討論的共同問題；若在作答前先看到別人的討論，等於先看到答案，前測就不成立了。
教師與研究者不受此限（要在課前備課、課後分析）。

右上角可切換班級、身分、字級、高對比與外觀。四個班級分別被分派到
**導師／學生／同儕／對照**四個條件——中山國小五年 3 班（導師）、五年 4 班（學生）、
仁愛國小六年 1 班（同儕）、六年 2 班（對照）——換成不同班的學生就會看到不同的夥伴，
對照組看到的是同尺寸的「我的筆記」。知識建構空間的種子貼文只種在五年 3 班。

## 無障礙

宣告目標為 WCAG 2.2 AA。已實作：

* 基準字級 **20px**，右上角可切換 100% / 125% / 150% / 175%（＝ 20 / 25 / 30 / 35px），設定會持久化
* 高對比模式（`data-contrast="high"` 覆寫 23 個色彩 token），內文對比下限 4.5:1、表單與圖形邊界 3:1
* 不以顏色單獨傳達訊息：AI 條件用形狀符號（▲●■◇）、理解歷程用形狀符號（▲●■◆）、
  已標記的句子除了底色還加一個「▍」字元記號
* 全鍵盤可操作：文本的每一句都是原生 `<button aria-pressed>`，不是可點的 `<span>`
* 焦點可見：`:focus-visible` 3px 外框
* 自然文件流版面（不是固定視窗高度的 app shell），200% 放大不橫向破版
* `prefers-reduced-motion` 一次關掉全部動效
* 字級、高對比、外觀三個切換都會透過 `role="status" aria-live="polite"` 播報

學生實際要讀的內容都在 20px 以上（文本 21px、題幹／選項／對話／自我檢核 20px），
且四個字級檔位都等比放大——型級與所有元件都用 `rem`，基準字級掛在 `:root` 上。

**尚未達成的部分**見 [docs/系統設計說明.md §12.2](docs/系統設計說明.md)——
主要是介面的次要標籤（pill、表格、說明文字）在 100% 時仍為 16–17px，
以及 WCAG 1.4.10 要求的 400% / 320px 尚未逐頁驗證。

## 注意

* 內建的班級、作答、貼文與對話**全部是模擬資料**，由固定亂數種子產生（每次載入結果一致），
  僅供展示與方法討論，不得當成實徵結果引用。
  示範資料的四條件差異是**依理論預測寫進生成器的**，用來示範分析管線能不能把差異抓出來。
* 文本與題目是**自編的 PIRLS 風格示範素材**，不是官方釋出文本或原題。
* 問卷題項是**依構念自撰的示範題**，不是已驗證量表的中譯本（10 個構念、41 題）。
  正式施測請改用公開的驗證量表（詳見 [docs/系統設計說明.md §7](docs/系統設計說明.md)）。
* 條件在班級層次操弄，平台的 ANCOVA 以學生為分析單位，未處理班級內相依；
  嚴謹分析應採多層次模型。中介估計的是觀察變項路徑模型，不是含潛在變項的 SEM。
* 資料存在瀏覽器的 `localStorage`，換裝置或清除資料就會消失。
  「系統設定 → 重設為示範資料」可還原。
* AI 助評預設使用**內建規則引擎**（離線、可重現）。要改用外部語言模型，
  在「系統設定」選一個服務提供者（OpenAI／DeepSeek／Gemini 的 OpenAI 相容端點，或自訂端點）
  並填入 API key——**出廠預設的端點與模型需先改掉**。
  瀏覽器直連這些端點多半會被對方的 CORS 政策擋下，
  因此線上版建議一律使用內建規則引擎（所有分析功能都不會少）。

## 部署

`src/` 是唯一的真實來源。推送到 `main`（或在 Actions 頁面手動 `workflow_dispatch`）之後，
[`.github/workflows/pages.yml`](.github/workflows/pages.yml) 會在 CI 重新執行 `build.sh`、
驗證產物存在且非空、確認 `<title>KAIROS</title>` 確實在產物裡（改名回退會直接讓 CI 失敗），
接著把 `README.md` 與 `docs/*.md` 複製到 `dist/docs/`，最後把整個 `dist/` 部署到 GitHub Pages。
本 README 因此也會發布為線上的 `/docs/README.md`。

workflow 用 `actions/configure-pages@v5` 搭配 `enablement: true`，
第一次執行就會自動把 repo 的 Pages 打開並設為由 GitHub Actions 建置。

`dist/index.html` 也有進版控，因此可以直接下載單檔在本機或校內網路離線使用。

repo 裡另有 `streamlit_app.py`：這個 repo 原本是 Streamlit Community Cloud 的範本，
若你已經接上 Streamlit，它會把同一份 `dist/index.html` 嵌進去。
但 Streamlit 是沙箱 iframe，localStorage 通常會被擋，
你新增的貼文與作答不會保存——**正式使用請走 GitHub Pages**。

## 開發

`src/` 內的檔名前綴決定串接順序，`build.sh` 只收 `3*`–`9*` 的 `.js`（共 19 個），
所以 `zz-debug.js` 不會進正式版。需要逐階段自我檢測時：

```bash
{ cat dist/index.html; echo '<script>'; cat src/zz-debug.js; echo '</script>'; } > dist/debug.html
```

開啟 `debug.html`，左下角會逐一列出 68 個渲染與計算階段的耗時與錯誤。
把分頁放在前景再開——背景分頁的 `setTimeout` 會被瀏覽器節流，整輪會跑得非常慢。
